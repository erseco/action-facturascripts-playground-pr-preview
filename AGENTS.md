# AGENTS.md -- AI Agent Guide for action-facturascripts-playground-pr-preview

## Origin and Attribution

This project is part of a family of "Playground PR Preview" GitHub Actions that post
a browser-preview link on pull requests. Sibling actions target other in-browser
runtimes (e.g. Moodle Playground, Omeka S Playground). This one targets
[FacturaScripts Playground](https://erseco.github.io/facturascripts-playground/), a
browser-based build of the FacturaScripts ERP/accounting suite.

- **This repo:** `erseco/action-facturascripts-playground-pr-preview`
- **Companion project:** `erseco/facturascripts-playground` -- the browser-based
  FacturaScripts runtime this action links to.

## What This Project Does

This is a **GitHub Action** that adds a "Preview this PR in FacturaScripts Playground"
button/comment to pull requests. When a contributor opens a PR, the action builds a
FacturaScripts Playground blueprint from the PR's plugin/extension ZIP, encodes it into
a preview URL, and posts that link to the PR (as a sticky comment by default, or inside
the PR description).

The action does **not** build, test, or deploy anything. It only:

1. Reads action inputs (chiefly `zip-url`) and PR metadata.
2. Synthesizes a FacturaScripts Playground blueprint JSON.
3. base64url-encodes the blueprint and builds a preview URL.
4. Posts/updates the link on the PR (sticky comment or managed description block).

The plugin ZIP is expected to already exist at a public URL (typically a GitHub
archive URL for the PR head branch). This action does not create it.

## How to Build

```bash
npm install
npm run build    # runs: esbuild index.js --bundle --platform=node --target=node20 --format=cjs --outfile=dist/index.cjs
```

esbuild bundles `index.js` + its `node_modules` dependencies into a single
`dist/index.cjs`. GitHub Actions runs `dist/index.cjs` directly (see `action.yml`
`runs.main`). **Always rebuild and commit `dist/index.cjs` after editing `index.js`
or `lib.js`** -- CI's `verify-dist` job fails if the committed bundle diverges from a
fresh build.

## Source Code Architecture

The code is split into two files with a clean separation:

- **`lib.js`** -- pure functions with no side effects: blueprint construction, base64url
  encoding, URL building, comment/description templating, and the sticky-block regex
  helpers. Everything the unit tests exercise lives here.
- **`index.js`** -- the Actions entry point (`run()` IIFE). It reads inputs via
  `@actions/core`, resolves the PR (from the `pull_request` event payload or via the
  GitHub API when `pr-number` is set), builds the blueprint + preview URL by calling
  into `lib.js`, and publishes to the PR via Octokit.

### Execution Flow (`index.js`)

```
1. Read inputs (github-token, zip-url, title, description, author, playground-url,
   image-url, comment-marker, extra-text, mode, restore-button-if-removed,
   pr-number, extra-plugins, seed-json, blueprint-json, landing-page, debug-enabled,
   site-title, site-locale, site-timezone, login-username, login-password).
2. Validate mode ('comment' or 'append-to-description'); fail on anything else.
3. Resolve PR context:
   - From context.payload.pull_request (pull_request trigger), OR
   - From octokit.rest.pulls.get when pr-number is provided (workflow_run trigger).
4. Build blueprint via buildBlueprint(...) and JSON.stringify it.
5. Build preview URL via buildPreviewUrl(...).
6. Warn (do not fail) if the preview URL exceeds MAX_SAFE_PREVIEW_URL.
7. Set outputs (preview-url, mode) and publish:
   - append-to-description: update PR body with a managed :start/:end block.
   - comment (default): clean any leftover description block, then create/update
     a sticky comment identified by the hidden marker.
8. Set remaining outputs (comment-id, rendered-description).
```

### Key Constants

| Constant | Where | Value | Purpose |
|---|---|---|---|
| `MODE_COMMENT` | `index.js` | `'comment'` | Default publish mode; posts a sticky PR comment |
| `MODE_APPEND` | `index.js` | `'append-to-description'` | Embeds a managed block in the PR body |
| `MAX_SAFE_PREVIEW_URL` | `lib.js` | `8000` | Preview-URL length above which a web server may reject the request (HTTP 414). nginx caps the request line at 8 KB by default; we warn a little under that. |
| `commentMarker` (input default) | `action.yml` | `facturascripts-playground-preview` | Hidden HTML marker used to dedupe the sticky comment and as the base for `:start`/`:end` description markers |

### Blueprint Schema

`buildBlueprint()` produces a FacturaScripts Playground blueprint. The minimal shape,
from just `zip-url`:

```json
{
  "meta": {
    "title": "PR Preview",
    "author": "erseco",
    "description": "Preview this PR in FacturaScripts Playground"
  },
  "plugins": [
    "https://github.com/OWNER/REPO/archive/refs/heads/BRANCH.zip"
  ]
}
```

Optional sections are added only when the corresponding input is supplied:

| Blueprint key | Populated from | Notes |
|---|---|---|
| `meta.title` / `meta.author` / `meta.description` | `title` / `author` / `description` | Always present |
| `plugins` | `zip-url` + `extra-plugins` | `zip-url` is always first; entries deduplicated and trimmed |
| `landingPage` | `landing-page` | Path opened inside the Playground |
| `debug.enabled` | `debug-enabled` | Boolean |
| `siteOptions.title` / `.locale` / `.timezone` | `site-title` / `site-locale` / `site-timezone` | Section omitted entirely if all unset |
| `login.username` / `.password` | `login-username` / `login-password` | Section omitted entirely if all unset |
| `seed` | `seed-json` | Arbitrary seed data (customers, suppliers, products, ...) |

Finally, `blueprint-json` (if provided) is **deep-merged last** over the generated
object via `mergeBlueprint()`, letting a caller add or override any advanced setting.
Arrays in the override replace (do not concatenate) the base value, and the resulting
`plugins` array is deduplicated again.

### Preview URL Encoding

FacturaScripts Playground receives the blueprint via a single query parameter:

```
https://erseco.github.io/facturascripts-playground/?blueprint-data={base64url-encoded-json}
```

The blueprint JSON is base64url-encoded (RFC 4648 §5: `+`→`-`, `/`→`_`, padding
stripped) so it is URL-safe without percent-encoding.

**URL-length warning:** a large blueprint (many `extra-plugins`, big `seed-json`, a
large `blueprint-json` override) can make the preview URL long enough that a web server
rejects it with **HTTP 414 (URI Too Long)**. After building the URL, `index.js` calls
`previewUrlExceedsLimit(previewUrl)`; if the URL exceeds `MAX_SAFE_PREVIEW_URL` (8000
chars) it emits a `core.warning(...)` suggesting the user trim `extra-plugins`/
`seed-json` or split the payload. This is **advisory only** -- the action still
publishes the link and does not fail.

### Publish Modes

The `mode` input selects where the preview goes. Both modes are idempotent across
repeated workflow runs (`synchronize`, `edited`, reopen, etc.).

**`comment` (default)** -- posts a *sticky* PR comment:

- The comment body is prefixed with a hidden `<!-- facturascripts-playground-preview -->`
  marker.
- On each run the action paginates existing PR comments (100 per page) looking for that
  marker; if found it **updates** that comment, otherwise it **creates** a new one --
  so there is never more than one preview comment.
- Cross-mode cleanup: before posting, it calls `removeDescriptionBlock()` to strip any
  leftover managed block from the PR body, so the preview lives in exactly one place if
  the user previously used `append-to-description`.
- Sets output `comment-id`.

**`append-to-description`** -- embeds a managed block in the PR body:

```html
<!-- facturascripts-playground-preview:start -->
## FacturaScripts Playground Preview
...preview button/link...
<!-- facturascripts-playground-preview:end -->
```

- On subsequent runs `computeNextDescriptionBody()` finds and replaces this block.
- **Placeholder detection:** if the user replaced the content between the markers with
  their own text (not something that looks like a Playground button), the function
  returns `null` and the action leaves the body untouched.
- **Restore behavior:** if the block/markers are gone and `restore-button-if-removed`
  is `false`, it returns `null` (stays removed); if `true` (default), it re-appends the
  block.
- Sets output `rendered-description`.

## CI Workflows

### ci.yml

Runs on push to `main` and PRs to `main`. Two jobs: **Test** (`npm ci` + `npm test`)
and **Verify dist/** (`npm run build`, then fails if `git status --porcelain dist/`
is non-empty -- i.e. the committed bundle is stale). Do not modify these jobs as part
of unrelated changes; they are the guardrail that keeps `dist/` honest.

### dependabot-dist.yml

Runs on Dependabot PRs only. Rebuilds `dist/` and pushes the result back to the PR
branch, so bundler/dependency bumps don't leave `dist/` stale and trip `verify-dist`.

### publish-immutable-action.yml

Runs when a GitHub release is published; uses `actions/publish-immutable-action` to
publish the action version.

## Common Tasks for AI Agents

### Adding a new action input

1. Add the input under `inputs:` in `action.yml`.
2. Read it in `index.js` with `core.getInput('input-name')` (and parse via
   `parseJsonInput` / `parseOptionalBoolean` if it is JSON/boolean).
3. If it feeds the blueprint, thread it through the `options` object passed to
   `buildBlueprint(...)` and handle it inside `buildBlueprint` in `lib.js`.
4. Add/extend a unit test in `test/index.test.js`.
5. Update `README.md`.
6. Run `npm run build` and commit the regenerated `dist/index.cjs`.

### Changing the blueprint defaults or shape

Edit `buildBlueprint()` in `lib.js` (line 116). Keep it pure and covered by tests --
`test/index.test.js` asserts the exact object shape, dedup behavior, and the
`blueprint-json` override semantics. Adjust those assertions alongside the change.

### Testing locally

There is no live Playground harness in this repo; verify via unit tests:

```bash
npm test        # node --test test/index.test.js
```

Tests import pure functions directly from `lib.js`. To smoke-test the whole action,
push to a branch and open a test PR on a repo that consumes this action, then check the
PR comment/description.

### Publishing a new version

1. Ensure `dist/index.cjs` is current: `npm run build`, then commit.
2. Commit all changes and merge to `main`.
3. Create a GitHub release with a semver tag (e.g. `v1.2.3`).
4. Move the major-version tag (`v1`) to the release commit so
   `uses: erseco/action-...@v1` picks it up.

> **Important -- the `v1` tag currently lags `main`.** At the time of writing,
> `git log v1..main --oneline` lists ~14 commits that are on `main` but not reachable
> from `v1`, so consumers pinned to `@v1` are running an older bundle. Whoever cuts the
> next release should re-tag `v1` to the release commit and then confirm
> `git log v1..main --oneline` prints nothing before announcing it. Re-tagging is a
> separate, explicitly-confirmed step -- do not force-move the `v1` tag as a side
> effect of other work.
